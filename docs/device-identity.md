# 账号级设备身份（给使用者看的整体流程说明）

这个模块只做一件事：**让每个 TRAE SOLO CN 账号，各自持有一套独立的"设备身份"，这套身份被该账号的登录和刷新固定复用，不再所有账号共用一台设备身份。**

一句话版本：改之前，多账号共享同一个 deviceId / machineId（官方"一个设备能绑定的账号数量"很容易触顶）；改之后，每个账号从第一次登录起拿到自己独立的一套，登录、刷新、删除重加的行为都清晰可控。

---

## 一、这套"设备身份"包括什么

每添加一个账号，系统会给它记下一套 5 项信息：

1. **deviceId（设备号）** — 一串 15 位数字，后台用它认设备；
2. **machineId（机器号）** — 一串 32 位字符，配合设备号；
3. **硬指纹** — 设备名、品牌、系统版本；
4. **EC 密钥对** — 一把私钥 + 一把公钥，用来证明"这台设备不是我伪装的"。

这 5 项合起来，就是这个账号在该机器上的"固定身份证"。

---

## 二、整体的流程（大白话）

### 1. 首次登录一个新账号
- 系统在你保存这个账号时，**当场生成**一套完整身份（上面的 5 项）。
- 这套身份随账号快照**一起保存**在你本地。
- 账号整个生命周期里，登录、刷新、都拿这一套。

### 2. 之后再次登录同一个账号
- 系统先看**当前正在使用的账号**是不是我们已经保存过的。
- 是 → **直接复用**它原来那套身份（设备号、机器号、密钥全都不变）。
- 不是（新账号/不在列表里）→ 生成一套新的。

### 3. 后台自动刷新（保持登录）
- 刷新用的也是同一套身份 + 同一把密钥，所以和登录时显示的设备完全一致。

### 4. 删除账号 / 重新添加
- 删除账号时，**这套身份会跟着账号一并删除**（不会留底、不回收复用）。
- 之后重新添加这个账号 = 当新账号处理 → **生成一套全新的身份**。

> 规则一句话：**不删就是同一台机器；删了重加就是新的一台机器。**

## 三、这个模块的真实价值（结论）

核心价值是**规避"同设备绑多号"触顶**，而不是"跨会话固定"：

- **开发前（main）**：多账号共用同一个共享 user-data 目录，登录时从同一个 storageRoot 读到同一个 `deviceId` 和同一个 `machineId` → 所有账号挤在同一台设备身份上，官方"单设备可绑定账号数"上限很容易被触发。
- **开发后**：每个账号在登录时从各自快照的 `deviceIdentity` 读取独立 deviceId / machineId / 密钥 → 从计数上把账号分散到不同设备身份，不再"一台设备挂 N 个账号"。

### 残余风险（未规避的部分）

- `deviceName` / `deviceBrand` / `osVersion` 仍共享真机值（来自 `os.hostname()`、`PROCESSOR_IDENTIFIER` 等机器级指纹），官方仍能看到"同一台物理机"。
- 本模块只分开了 deviceId/machineId 层面的"同设备绑多号"计数，不改变"同一台真机上开了 N 个账号"这一事实；彻底分散需要多台硬件/真机指纹，那不属于本模块范围。

---

## 四、不会改变的东西

- **签到（每日领取）的 `x-device-id` 仍是账号 userId**，与本模块无关（这是硬性规则，不能动）。
- 刷新 UA、签到节奏、登录参数（`solo` 登录、隐藏 SaaS 登录）等**一概不变**。
- 系统不会去逆向或伪造官方行为。

## 五、你现在要做的验收（按你本地的替换测试方法）

> 你在本机是用 exe 安装的。下面是和你操作计划一一对应的步骤。

### 准备
1. 先**关闭**当前运行的 TRAE 增强助手（右键托盘 → 退出/停止），静置几秒。
2. **卸载**旧版 exe。
3. **安装**我给你的新安装版 exe（装完会用桌面快捷方式隐藏启动）。

### 步骤 A：验证"新账号第一次登录生成身份"
1. 打开增强助手，**添加/登录**一个账号。
2. 找到账号数据目录，打开该账号的 `snapshot.json`：
   - 在文件**顶层**能看到一个 `deviceIdentity` 字段（里面有设备号、机器号、密钥等）→ **通过**。
   > 数据目录一般在系统 `data\accounts\<账号id>\snapshot.json`（便携版在该 exe 同目录的 `data\` 下）。

### 步骤 B：验证"同一账号再次登录身份不变"
1. 把这个账号从 TRAE 里登出，再**重新登录**（账号仍在增强助手列表里）。
2. 再打开它的 `snapshot.json`，对比 `deviceIdentity` 里的：
   - `deviceId`、`machineId`、`privateKeyPEM` —— **和之前完全一样** → **通过**（说明复用了，没每次换新身份）。

### 步骤 C：验证"删除账号后重新添加 = 换全新身份"
1. 这是你计划里的关键一步：**手动删除这个账号**（增强助手列表里删除）。
2. 检查其数据目录：对应账号的文件夹已**随之消失**（设备身份一并删掉）。
3. **重新添加**同一个账号。
4. 再打开新 `snapshot.json` 的 `deviceIdentity`：
   - `deviceId` / `machineId` / `privateKeyPEM` —— **都和删除前的不同** → **通过**（删了重加 = 新身份）。

### 结果确认
- A、B、C 三步都符合预期 → 本功能验收通过。
- 验收通过后告诉我，我再按发布流程打标签发布。

## 七、附录：技术实现要点（给开发参考，看不明白可跳过）

- 新增 `src/lib/device-identity.js`：`mintDeviceIdentity` 生成 / `readDeviceIdentity` 读取 / `isDeviceIdentity` 校验。
- `collectLoginContext`(trae-product.js)：有已存身份则复用，否则生成，登录全程只上报一套。
- `trae-oauth.js`：`start()` 用 `resolveActiveAccount` 命中活跃账号的已存身份；`exchangeAuthCode` 复用 `context.keyPair`，不再每次换钥；`buildStorageRoot` 把身份落盘。
- `trae-storage.js`：`extractAuthSnapshot` 透传、`validateAuthSnapshot` 校验顶层 `deviceIdentity`。
- `trae-refresh.js`：刷新优先从快照 `deviceIdentity` 重建设备信息，与登录指纹一致。
- `trae-checkin.js`：**不改**（签到 `x-device-id` 仍用 userId）。
- 测试：`npm test` 279 项全绿；`npm run check` 通过；`build:exe` 自校验通过。
- **当前状态**：代码已提交在 `feature/device-identity` 分支（已合并最新 `main`），尚未推送、未发布。模块的核心价值是**将多账号从共享同一 deviceId/machineId 的"单设备绑多号"触顶风险，拆分为每账号独立的 deviceInfo**；残余硬指纹（deviceName/deviceBrand/osVersion）仍共享真机值，属预期范围。验收通过后再按 `docs/RELEASE_FLOW.md` 走发布。
