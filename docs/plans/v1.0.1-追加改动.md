## 1. 起因：两条实测结论

### 1.1 WorkDaddy 的签到不是"点账号触发"

赵总的印象是"WorkDaddy 里点账号，没签到就自动签到"。实测**不成立**，真实机制是这样：

签到是**一条可编辑的自动化任务**，定义在 `WorkDaddy/scripts/builtin/automations/daily-account-checkin.json`：

| 项 | 值 |
|---|---|
| `id` / `name` | `daily-account-checkin` / 循环账号静默签到 |
| `trigger.types` | `["clientLoaded", "panelOpened"]`，`oncePerNavigation: true` |
| `schedule` | `{ type: "interval", minutes: 60 }` |
| `steps` | `account.forEach`（`accounts: "all"`, `switch: false`）→ `account.checkin` |

关键证据：

- 事件发射点：`WorkDaddy/scripts/inject.js:7070` —— **面板从"关"变"开"**时
  `POST /api/automations/events { type: "panelOpened" }`（`options.automation` 为真时不发）
- daemon 另有"启动 30 秒后补签"（`WorkDaddy/scripts/daemon.js:285` 的版本注记）
- 账号卡片按钮只有「设为主账号 / 切换（两击确认）/ 删除」，卡片本身**没有绑定 click**
- 面板自身注释（`WorkDaddy/scripts/inject.js:10`）：
  "每日签到由自动化任务管理，账号页只显示当天已确认的签到状态"

**结论**：赵总看到的"点账号就补签"，实际是"**打开面板就补签**"——徽章从「待签到」翻成
「已签到」，看起来像点账号触发的。

### 1.2 本项目现状与差异

本项目的签到触发点只有 3 个（`runAccountCheckin()` 的调用点全集）：

| 触发点 | 位置 | `reason` |
|---|---|---|
| 启动后 5 秒首跑 + 每 30 分钟 | `src/daemon.js:1650` / `1652` | `scheduled` |
| `POST /api/accounts/panel-open` | `src/daemon.js:1072` | `panel` |
| `POST /api/checkin/run` | `src/daemon.js:1179` | `manual` |

账号切换**不触发**签到。间隔是硬编码常量 `AUTO_CHECKIN_INTERVAL_MS`（`src/daemon.js:114`）。

与 WorkDaddy 的差异：

| 差异 | WorkDaddy | 本项目 |
|---|---|---|
| 周期 | 60 分 | 30 分 |
| 启动后首跑 | 30 秒 | 5 秒 |
| 页面/客户端加载触发 | 有 | **没有** |
| 是否可配置 | 是（可改频率、改触发、可禁用） | **硬编码** |

**主干一致的三点**（已照搬对）：今日已确认则跳过、用各账号自己的 token 不切换客户端、
打开面板会补签。

### 1.3 首装"无账号"的真相

首装后第一次开面板，`src/ui/inject.js` 的 `openPanel()` 本该自动纳管当前账号：

```js
if (data?.accounts && !data.currentAccountId) {
  const backup = await autoBackupCurrent();   // → POST /api/accounts/backup
  if (backup) data = await refresh();
}
```

条件在首装必然满足（`resolveActiveAccount()` 返回 `{ id: null, state: "not-managed" }`
→ `currentAccountId` 为 `null`）。所以**面板停在"暂无账号"意味着这次纳管失败了**，而它：

- 面板侧 `autoBackupCurrent()` 里 `catch { return null; }` —— **无提示、无状态行、无日志**
- daemon 侧顶层 catch 只 `jsonResponse(500, {error})` —— **不写日志**

于是"纳管失败"与"你还没加账号"在界面上完全同形，且事后无痕可查。
赵总后来再开面板就正常了 —— 说明**第二次尝试成功**，只是第一次的失败被吞了。

## 2. A：自动签到可配置

### 2.1 已拍板的三条（赵总 2026-09-17）

1. **间隔用固定档位下拉**：15 / 30 / 60 / 120 分钟。不做自由输入。
2. **默认值保持现行为**：`auto: true`、`intervalMinutes: 30`、`onClientLoad: true`
   —— 老用户零感知。
3. **开关只控"自动那两路"**（定时 + 页面加载）。
   **开面板补签**与**「立即签到」按钮**是用户主动行为，**不受开关约束**。

### 2.2 配置键

`data/config.json` 增加第 4 个顶层键：

```json
{
  "traeExe": null,
  "proxy": { "mode": "system", "url": null, "noProxy": "" },
  "traeUpdate": { "suppress": true, "previousMode": null },
  "checkin": { "auto": true, "intervalMinutes": 30, "onClientLoad": true }
}
```

改动位置：`src/lib/app-config.js` 的 `normalizeConfig()`。它现在 `return` 三个键
（两处：`raw` 为空时的默认分支 + 正常分支），**两处都要加**。

新增导出：

```js
export const CHECKIN_INTERVALS = [15, 30, 60, 120];
export const CHECKIN_DEFAULTS = { auto: true, intervalMinutes: 30, onClientLoad: true };
```

### 2.3 校验与迁移

新增内部函数 `normalizeCheckin(raw)`，照 `normalizeTraeUpdate` 的写法：

| 字段 | 规则 | 不合法时 |
|---|---|---|
| `auto` | 严格布尔 | 回落 `true` |
| `intervalMinutes` | 数字或纯数字字符串，且 `Number()` 后**恰好等于** 15/30/60/120 之一 | 回落 `30` |
| `onClientLoad` | 严格布尔 | 回落 `true` |

- 旧配置**没有** `checkin` 键 → 补齐默认，行为与 v1.0.1 完全一致，**零迁移成本**
- 不合法值**静默回落**（不抛错、不返回 400），因为面板只给 4 个档位，正常不可能触发；
  且响应会回显真正生效的值，不会骗人

### 2.4 接口契约

**`GET /api/settings`** 响应增加一段（现有 `network` + `traeUpdate` 不动）：

```json
"checkin": {
  "auto": true,
  "intervalMinutes": 30,
  "onClientLoad": true,
  "options": [15, 30, 60, 120]
}
```

`options` 由 daemon 提供，**面板不自己硬编码一份**，避免两边白名单漂移。

**`POST /api/settings/checkin`** 请求（三个字段都可选，缺省保持现值，照
`/api/settings/trae-update` 的先例）：

```json
{ "auto": false, "intervalMinutes": 60, "onClientLoad": true }
```

响应：

```json
{ "ok": true, "checkin": { "auto": false, "intervalMinutes": 60, "onClientLoad": true } }
```

副作用：

1. 写 `data/config.json`（走既有 `saveAppConfig`，原子写 + `0600`）
2. **原地重建定时器**，不重启 daemon 进程
3. 日志一条：`[settings] checkin auto=… interval=… onClientLoad=…`

`auto` 与 `onClientLoad` 都关时，间隔值仍照原样保存（不清零），下次开启沿用。

### 2.5 daemon 行为

现状（`src/daemon.js:1619-1655`）：

```js
const runScheduledCheckin = async () => { /* 7 个 in-flight 标记检查 → Cockpit 策略 → runAccountCheckin */ };
autoCheckinStartTimer = setTimeout(runScheduledCheckin, 5000);
autoCheckinTimer = setInterval(runScheduledCheckin, AUTO_CHECKIN_INTERVAL_MS);
```

改动：

**(a) 间隔改为读配置** —— `AUTO_CHECKIN_INTERVAL_MS` 常量删除（它在本轮改动后不再被
引用，属于本次改动产生的孤儿）。

**(b) 抽成可重建的调度函数**：

```js
function scheduleAutoCheckin({ initialRun = false } = {})
```

- 清掉已有 `autoCheckinTimer` / `autoCheckinStartTimer`
- `checkin.auto === false` → 不再建定时器，日志
  `[checkin] automatic check-in is disabled by configuration`
- 否则按 `intervalMinutes` 重建 `setInterval`
- **`initialRun` 只在 daemon 启动路径传 `true`**（保留"5 秒首跑"）。
  改配置时传 `false` —— 否则每次动设置都会立刻签一次，属于意外副作用

**(c) 页面加载触发** —— 扩展 `src/daemon.js:1541` 的 `onStateChange`
（CdpClient 在 `src/cdp/client.js:137` 连上时回调 `true`，`:62/128/133` 断开时回调 `false`）：

```js
onStateChange: (connected) => {
  cdpConnected = connected;
  if (!connected) { clientLoadCheckinDone = false; return; }   // 断开时复位
  if (clientLoadCheckinDone) return;                            // 每次连接只跑一次
  clientLoadCheckinDone = true;
  void maybeRunClientLoadCheckin();                             // 回调是同步的，不能阻塞
}
```

`maybeRunClientLoadCheckin()`：

- **实时读当前配置**，`auto && onClientLoad` 都为真才继续
- 复用 `runScheduledCheckin` 那一套（互斥标记 + Cockpit 策略），只是 `reason: "client-load"`
- 语义等价 WorkDaddy 的 `clientLoaded` + `oncePerNavigation: true`
  —— **TRAE 中途重启后，daemon 一重连就立刻补签**，不用等定时、也不用先开面板

**(d) 与"启动首跑"撞车的处理** —— 不需要新机制。`runScheduledCheckin` 开头已有 7 个
in-flight 标记检查，两个触发同时到达时后到者直接 return，而先到者正在跑同一件事。

**(e) 一个实现陷阱（必须注意）** —— `onStateChange` 与定时器都**不能在启动时闭包捕获
配置**。`POST /api/settings/checkin` 改完配置后，后续触发必须读到新值。
实现上用模块级变量（由设置接口更新）或每次调用时 `loadAppConfig()`，**不要**把
启动时那份 `config` 关进闭包。这是本轮最容易写错的一处。

**(f) `panel-open` 与手动按钮不判断配置** —— 赵总已定，两者不受 `auto` 约束。
所以 `src/daemon.js:1032` 的 `panel-open` 分支**不需要**加配置判断。

## 3. B：首装"静默失败"治理

### 3.1 A —— 让它不再骗人

改三处：

1. **`autoBackupCurrent()` 返回值** —— 不再 `catch { return null }`，改为
   `{ ok: true, account }` / `{ ok: false, error }`
2. **空态渲染** —— 两种状态分开：
   - 纳管成功但确实没有账号 → 维持「暂无账号备份」
   - 纳管失败 → 「自动纳管当前账号失败：{原因}」+ 一个**「重新尝试」**按钮
3. **daemon 侧补日志** —— 在 `/api/accounts/backup` 的处理分支内 `try/catch`，
   出错先 `console.error("[backup] …")` 再回 500。
   **不动**顶层 catch 的通用行为（那是所有接口的公共兜底，改它超出本轮范围）

### 3.2 C —— 纳管搬到 daemon

**现状的问题**：这件事由**面板**发起，只在"打开面板"那一刻试一次，失败就没有第二次机会。

**改法**：daemon 在**首次 CDP 连上**后（`onStateChange(true)`）判断：

- `accounts.length === 0`
- 且 `resolveActiveAccount()` 能认出当前登录身份

→ 执行一次 `backupCurrent()`，成功后 `notifyAccountsUpdated(cdpClient)`，
面板自动出现在列表里。

约束：

- **只跑一次**（`startupAdoptDone` 标记，成功失败都置位），避免循环重试
- 失败写日志：`[adopt] could not adopt the current account: …`
- **幂等性已核实**：`src/lib/accounts.js:165` 的 `backupCurrent` 以
  `accountId = acct_${stableHash(identityKey)}` 定位，命中则 upsert，返回
  `createdSnapshot: !existing` —— 所以 daemon 与面板**双路径都调是安全的**，
  最坏只是刷新一次快照（这是想要的行为）
- 面板侧那条 `autoBackupCurrent()` **保留**，作为用户主动开面板时的补救路径。
  它不再是唯一机会，但也不该删

**收益**：不开面板也会自动纳管（TRAE 登录完 daemon 就接管了），
且不再依赖"面板打开那一次"的时序运气。

### 3.3 面板仍然是纯视图

C 把工作放在 daemon 侧，**没有**引入任何面板轮询。`AGENTS.md` 的约定
（"The injected panel is a pure view … Nothing polls"）继续成立。
选择这个方案而不是"面板里做定时重试"，就是为了不破这条。

## 5. 验收点

本轮改的是配置层 + daemon + 面板三层，光跑测试不够。交付前至少覆盖：

1. `npm run check` + `npm test` 全绿
2. `node scripts/service.js status` 真跑一次（验证 ESM 链接期，堵 `node --check` 不解析 import 的假绿）
3. **隔离实例接口自检**（独立 `TRAE_ENHANCER_UI_PORT` / `CDP_PORT` / `DATA_DIR`，
   禁止碰赵总正在跑的 daemon 与 TRAE）：`GET /api/settings` 出现 `checkin` 段；
   `POST /api/settings/checkin` 四档各改一次并回读；`auto=false` 时改一次再回读
4. 真机面板：设置 tab 新块的三个控件、关闭后的禁用态、About 页文案联动
5. 首装路径（**只能在内网或干净环境验**）：首次开面板不再出现"无账号且无提示"；
   若纳管失败必须看到原因

第 4、5 项需要活的 TRAE 渲染进程，按既有约定**不在开发机上打断赵总的使用**。

## 8. 风险

| 风险 | 说明 | 对策 |
|---|---|---|
| 闭包捕获旧配置 | `onStateChange` / 定时器若捕获启动时的 config，改设置不生效 | 第 2.5(e) 条已点明；实现后必须用"改一次设置再回读"验收 |
