## 0. 四个问题的根因结论

| # | 现象 | 根因（已在代码中定位） |
|---|---|---|
| 1 | 助手启动后账号实际已签到，面板仍显示"待签到" | `src/ui/inject.js:1087` `accountCheckinView()` **由面板自己算**：读本地 `account.checkin` 与本地日期比对。daemon 侧没有当天记录就永远显示"待签到"，与服务端真实状态脱钩。且整个 `inject.js` **没有任何 `setInterval`**，daemon 状态变化不会通知面板。 |
| 2 | 导入账号后同样显示"待签到" | `src/ui/inject.js:1853` 导入成功后只 `await refresh()`，不触发任何对账；`src/lib/accounts.js:303` `importSnapshots()` 只写认证快照与身份，不写 `checkin` / `insights` 元数据 → 导入的账号天然没有签到记录与额度。 |
| 3 | 内网安装后调官网地址报错 | daemon 内的 `fetch` 走 Node，默认**忽略**代理。TRAE 自己走 Chromium，跟随 Windows 系统代理（`HKCU\...\Internet Settings`）→ 表现为"TRAE 正常，助手才报错"。现有 `useEnvProxy` 只读 `HTTP_PROXY`/`HTTPS_PROXY` **环境变量**，而系统代理通常不写成环境变量，所以即使打开也无效。 |
| 4 | TRAE 总是自动更新 | 未写 `update.mode`；VS Code 系更新框架在该值为 `default` 时会自动检查。 |

问题 1、2 的现场是**内网那台机器**；本机 `data/accounts/index.json` 三个账号均为
`{date:"2026-09-16", checked:true, reason:"scheduled", reward:150}`，说明本机自动签到是通的，
因此这两项**无法在本机复现**，必须在内网机验收。

## 1. 修复 1 & 2：面板与 daemon 状态同步

采纳 WorkDaddy 的架构（其 `inject.js` 头部第 6 条设计约定：
"每日签到由自动化任务管理，账号页只显示当天已确认的签到状态"）。

### 1.1 daemon 侧：状态变更后经 CDP 推送事件

`src/daemon.js` 新增：

```js
const ACCOUNTS_UPDATED_EVENT = "trae-enhancer:accounts-updated";

async function notifyAccountsUpdated(cdpClient) {
  if (!cdpClient.isConnected) return false;
  try {
    await cdpClient.evaluate(
      `window.dispatchEvent(new CustomEvent(${JSON.stringify(ACCOUNTS_UPDATED_EVENT)}))`,
      { awaitPromise: false, timeoutMs: 3000 },
    );
    return true;
  } catch {
    return false;
  }
}
```

推送时机（每次都在**状态已落盘之后**）：

- 签到结束：`/api/checkin/run`、定时 `runScheduledCheckin`、新增的 panel-open 编排
- 额度刷新结束：`refreshAccountsInsights`
- 保活结束：`runAccountKeepalive` 及其定时器
- 账号导入、备份、切换完成之后

复用 `src/cdp/client.js` 已有的 `isConnected` getter 与 `evaluate()`，不新增通道、不开新端口。

### 1.2 面板侧：监听 + 防抖 + 拉取

`src/ui/inject.js` 新增监听：面板未打开时**直接返回，不发请求**；打开时 150ms 防抖后重新拉
`/api/accounts`：

```js
let accountsUpdatedPending = false;
window.addEventListener(ACCOUNTS_UPDATED_EVENT, () => {
  if (!panel.classList.contains("open") || accountsUpdatedPending) return;
  accountsUpdatedPending = true;
  setTimeout(() => {
    accountsUpdatedPending = false;
    if (panel.classList.contains("open")) refresh().catch(() => {});
  }, 150);
});
```

**循环防护（重要）**：此监听只做 `GET /api/accounts`，**绝不**触发
`/api/accounts/insights/refresh`，否则"刷新额度 → 推送 → 再刷新额度"会自激。

### 1.3 daemon 侧：面板打开编排（新增接口 `POST /api/accounts/panel-open`）

按你的选择"查询 + 自动补签到"实现。语义：

1. 任一操作在途（switch / checkin / keepalive / insights / login / fakeLogout）→ 立即返回
   `{ok:true, busy:true}`，**不报错、不弹 toast**。
2. Cockpit 分层探测（见 §3.2）判定为运行中 → 返回 `{ok:true, skipped:"cockpit"}`。
3. `runAccountCheckin(null, {force:false, reason:"panel"})` —— 已有实现天然幂等：
   `checkinOneAccount()`（`src/daemon.js:277`）先查服务端当天状态，已签到就只补写本地记录、
   **不重复领取**。这正是"实际已签到 → 自动纠正显示"的关键，无需新逻辑。
4. `refreshAccountsInsights(null)` 刷新额度。
5. `notifyAccountsUpdated()` 推送。
6. 返回 `{ok:true, checkedIn, skipped, failed, insights}` 摘要。

### 1.4 面板侧：打开与导入的调用点

`openPanel()`（`inject.js:1876`）改为：`refresh()` → 必要时 `autoBackupCurrent()` →
`POST /api/accounts/panel-open`（fire-and-forget）。仅当返回 `busy`/`skipped` 时，
才退回 v1.0.0 的 `shouldRefreshInsights()` + `refreshAccountInsights()` 路径 ——
这样既让 daemon 在空闲时统一编排，又不会因为 daemon 忙碌而丢掉额度刷新（无回归）。

`openImportDialog()`（`inject.js:1853`）在 `await refresh()` 后追加同一次
`POST /api/accounts/panel-open`，让新导入账号对账并刷新额度。

额度同步按你的选择调整为：**打开面板时必定刷新 + daemon 每次推送都带额度更新**。

### 1.5 面板显示"同步中"

`accountCheckinView()` 当前在无记录时直接返回"待签到"，容易误导。新增一个
`syncingCheckin` 标志：panel-open 编排在途时，未确认的账号显示"同步中"而不是"待签到"，
编排结束（收到推送或返回）后恢复。这样"其实已签到"的账号不会先被标成"待签到"再跳变。

## 2. 修复 3：代理配置

### 2.1 新增 `src/lib/system-proxy.js`

用 PowerShell 读注册表（`reg.exe` 安全策略下被拦，不能走）：

```
HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings
  ProxyEnable / ProxyServer / ProxyOverride / AutoConfigURL
```

解析 `ProxyServer` 的两种形态（`host:port` 与 `http=...;https=...;socks=...`），产出
`HTTP_PROXY` / `HTTPS_PROXY` / `NO_PROXY`。`ProxyOverride` 中的 `<local>` 展开为回环地址；
随后**始终**过一遍已有的 `ensureLocalNoProxy()`（`net-diagnostics.js:161`），保证
`127.0.0.1` / `localhost` / `::1` 永不走代理 —— 与 AGENTS.md 第 153 条一致。

两条必须诚实报错的路径：

- 只配了 PAC（`AutoConfigURL`）而没有 `ProxyServer`：Node 无法解析 PAC，明确提示
  "检测到自动配置脚本，助手无法解析，请在手动模式填入代理地址"，**不静默失败**。
- `ProxyServer` 里带 `user:pass@` 时，回显一律走脱敏，**不落盘、不入日志**
  （AGENTS.md 第 146 条）。

### 2.2 配置结构（`src/lib/app-config.js`）

`useEnvProxy: boolean` 扩展为：

```json
{ "proxy": { "mode": "system" | "manual" | "off", "url": "http://host:port", "noProxy": "" } }
```

- 默认 `mode: "system"`（跟随系统）。
- 向后兼容：读到旧 `useEnvProxy: true` → 迁移为 `{mode:"manual", url:null}`，
  `url` 为空时继续读 `HTTP_PROXY`/`HTTPS_PROXY` 环境变量，即 v1.0.0 的行为，老用户不炸。
- `proxyChildEnv()`（`net-diagnostics.js:178`）改为接收解析好的代理三元组，而不是布尔值。
  调用点三处同步更新：`src/launcher.js:79`、`scripts/service.js:305`、`scripts/watchdog.js:107`。

**关于"默认跟随系统"是否安全**：AGENTS.md 第 150-152 条要求该开关默认关闭，理由是
"不要弄坏当前直连的机器"。跟随系统模式在**没有**配置系统代理的机器上检测结果为空 →
行为等价于关闭，因此不会破坏直连机器；只有 Windows 真的配了代理时才会启用。
该条不变量的措辞需要同步更新，这不是绕过它。

### 2.3 新增 daemon 接口

- `GET  /api/settings/network` → 当前模式、系统代理探测结果（脱敏）、代理环境变量报告、生效状态
- `POST /api/settings/network` → 写入 `config.json`
- `POST /api/settings/network/test` → **带候选配置**起一个子进程跑探测并对比直连/走代理
  （`NODE_USE_ENV_PROXY` 只在进程启动时读取，运行中的 daemon 改不了自己的环境；复用
  `src/lib/launch-spec.js` 的 `serviceSpec()` 与 `net --probe-only`，与
  `scripts/service.js:671` 的 `probeThroughProxy()` 同一套机制）
- `POST /api/daemon/restart` → 调 `service restart`，让新代理配置生效

保存后必须明确提示"需要重启守护进程才生效"，并提供一键重启，不能让用户以为保存即生效。

## 3. 修复 4 与扫描健壮性

### 3.1 TRAE 自动更新开关

写入 TRAE 的 `User/settings.json`：`update.mode: "manual"`。

- 该文件是 **JSONC**（允许注释），必须做**文本级定向改写**，不能 `JSON.parse` 后
  `JSON.stringify` —— 否则会抹掉用户注释。写前备份、失败回滚。
- 只动 `User/settings.json`，不碰安装目录与 `app.asar`（AGENTS.md 第 6-7 条）。
- 设置页开关默认**开**；首次自动写入时在面板给一次性提示，不静默改用户配置。
- 同时提供"恢复自动更新"（写回或删除该项）。
- 实现前需**重新实证**一次生效路径（`resources/app/out/main.js` 中 `getValue("update.mode")`
  的判定分支，以及 `update.enableWindowsBackgroundUpdates`、`extensions.autoUpdate`
  这几个**独立**机制是否也要一起关闭），并以"重启 TRAE 后不再检查更新"作为验收标准，
  不以读代码作为结论。

### 3.2 Cockpit 分层探测（`src/lib/trae-process.js:104`）

现状：只用 PowerShell `Get-Process`，一旦 `powershell.exe` 被安全策略拦掉（本机 `reg.exe`
就已被拦），`runPowerShell` 抛错 → `runScheduledCheckin`（`daemon.js:1062`）在
try 里抛错被 catch → **整轮扫描静默作废**。`logs/daemon.log` 里
`scheduled run failed: Command failed: powershell.exe ...` 就是这个。

改为分层：

1. `tasklist.exe`（原生系统程序，最不易被拦）
2. PowerShell `Get-Process`（现有实现）
3. 全部失败 → 返回 `unknown`

返回结构升级为 `{ running: true|false|null, source, error }`；现有 3 个调用点
（`daemon.js:764` 手动保活、`1062` 定时签到、`1099` 定时保活）分别适配。
任何一层失败都不再抛出中断扫描，并且 `unknown` **必须打警告日志**，不静默。

## 5. 已拍板

**（一）Cockpit 三层探测全失败（`unknown`）时的降级**

赵总答复："存在 cockpit 的情况非常少见" —— 即不该为一个罕见风险挡住正常签到路径。
据此采用比 A/B 都更精确的做法：

| 探测结果 | 签到 | 保活 | 凭据轮换 |
|---|---|---|---|
| `running: true` | 跳过 | 跳过 | 不轮换 |
| `running: false` | 进行 | 进行 | 允许 |
| `running: null`（unknown） | **进行**，打警告日志 | 跳过 | **禁止**（`authExpired` 记失败，不轮换） |

依据：AGENTS.md 第 33-34 条的冲突点是"**轮换**同一批 refresh token"，而
`checkinOneAccount()` 只在 `error.authExpired` 时才走 `refreshAuthSnapshot()` 轮换
（`daemon.js:316-320`）；正常签到（查询 + 领取）复用现有凭据，不构成轮换。
因此 unknown 时照常签到、但关掉轮换，既修好了内网问题 1、2，又不引入新的冲突面。

保活仍然在 unknown 时跳过：`keepaliveOneAccount()` → `refreshAccountKeepalive()`
**每次**都轮换凭据，是真正需要严格守卫的一方。

**（二）设置界面形态**：面板内新增第三个 tab「设置」。

与现有「账号」「关于」并列，直接扩展 `inject.js:789` 的 `te-tabs` / `te-pane` 结构。
好处：改动小、不用切窗口、自动继承面板现有的鉴权（`x-trae-enhancer-token`）与主题变量，
且不新增任何监听端口。
