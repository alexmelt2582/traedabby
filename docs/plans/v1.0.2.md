## 0. 为什么现在不做，以及缺口在哪

问题 3 修完之后，代理只有四种模式（`system` / `manual` / `env` / `off`），其中
`manual` 模式**只接受 `host:port`，不接受带凭证的 URL**：

- `src/lib/system-proxy.js:48` `proxyHasCredentials()` 检测 `user:pass@`
- `src/lib/app-config.js:94` `normalizeProxyUrl()` 命中即抛错

这不是"做不到"，是上轮**刻意设的防护**，理由写在 `app-config.js:80-84` 的注释里：
`config.json` 是明文 JSON，密码写进去就是未加密的密钥。当时的结论是"要认证就用
Windows 系统代理模式，让操作系统持有凭证"。

**这个结论有一个真实缺口**：TRAE 本身是 Chromium，走系统代理遇到 `407` 会自己弹框
让用户输密码并缓存；但守护进程是 **Node 子进程，拿不到 Chromium 输过的那个凭据**。
所以内网若使用需认证的代理，会出现"TRAE 能上网，助手的连通性探测 / 签到仍然 407 失败"。
v1.0.2 补的就是这个洞。

## 2. 本机实证结论（2026-09-16，一次性探针，已删除）

两件事都已实测，v1.0.2 开工时**不必重新调研**：

**（1）Node 认 URL 内嵌凭证。** 本机起一个返回 `407` 的代理，Node 子进程设
`NODE_USE_ENV_PROXY=1` + `HTTP_PROXY=http://alice:s3cret@127.0.0.1:<port>`，
代理端实收：

```
#1: CONNECT api.trae.cn:443 HTTP/1.1
     proxy-authorization: Basic YWxpY2U6czNjcmV0     ← base64("alice:s3cret")，完全一致
```

结论：把凭证拼进代理 URL 注入子进程环境**确实生效**，不需要额外实现认证握手。
（`NODE_USE_ENV_PROXY` 只在进程启动时读取，所以"保存后需重启守护进程才生效"
这条现有约束继续适用。）

**（2）Windows DPAPI 可用。** PowerShell 调
`[System.Security.Cryptography.ProtectedData]::Protect($bytes, $null, 'CurrentUser')`
成功，密文 308 字符 base64（`AQAAANCMnd8BFdERjHoAwE/C...`），`Unprotect` 解回原文一致。
本轮执行环境里 `reg.exe` 会被安全策略拦，但 PowerShell 可用。

结论：可以用 DPAPI 做 per-user 加密存盘，不必引入 native addon。

## 3. 设计方案（待实现，细节可调）

### 3.1 配置结构

```json
{
  "proxy": {
    "mode": "manual",
    "url": "http://host:port",
    "noProxy": "",
    "auth": {
      "username": "corp\\zhaoxian",
      "passwordEnc": "<DPAPI 密文 base64>"
    }
  }
}
```

- `passwordEnc` 是密文，`config.json` 中**永远不出现明文密码**。
- `auth` 为 `null` 表示代理不需要认证（现有行为完全不变）。
- `normalizeProxyUrl()` 的"拒绝带凭证 URL"校验**保留**：凭证走独立字段，不允许塞 URL。

### 3.2 新增 `src/lib/secret-store.js`（或 `dpapi.js`）

- `protectSecret(plain)` / `unprotectSecret(cipher)`，内部用 `spawn` 调
  `powershell.exe -NoProfile -Command -`，**明文通过 stdin 传入**。
- **绝不允许**把明文放进命令行参数（`-Command "...GetBytes('明文')"`）：
  任何能列进程命令行的工具都能读到它。这是本设计的第一条红线。
- daemon 启动时解密**一次**并缓存到内存（避免每次探测都 spawn 一次 PowerShell）。
- PowerShell 不可用 → 明确报错"本机不支持加密存储代理凭据"，**不静默降级**。

### 3.3 运行时注入

- `buildProxyVars()`（`system-proxy.js:248`）manual 分支：有 `auth` 时把凭证拼进
  `HTTP_PROXY` / `HTTPS_PROXY`；解密失败时返回 `reason: "auth-undecryptable"`。
- 解密失败**绝不能**返回"不带凭证的 URL"，那会让请求以匿名身份打代理并失败得更隐晦。
  必须让 `resolveProxyVars()` 明确失败，由调用点报"请重新输入代理密码"。

### 3.4 面板（设置 tab）

- `manual` 模式下显示「用户名 / 密码」两个输入框。
- 回显：只回显 `username`；**密码框始终留空**，留空表示"不修改"，
  勾选"清除"才删除 `auth`。不回填密文（无意义），更不回填明文。
- 保存时前端把明文 POST 给 daemon，daemon 侧加密后落盘。明文不经 CLI、不进日志。

## 4. 必须守住的安全不变量

1. 明文密码只存在于**内存**与**子进程环境变量**中；不落盘、不进日志、不进命令行。
2. 所有面向 UI / CLI / 日志的代理展示一律过 `redactProxyUrl()`（`system-proxy.js:32`）。
3. 明文密码不得写入 `config.json`、任何记忆文件、任何测试 fixture（测试用假值）。
4. 解密失败必须**显式报错**，不允许静默直连或匿名回退。
5. 沿用现有约束：`NO_PROXY` 恒含回环（`ensureLocalNoProxy()`），重启前 `stripProxyEnv()`。

## 7. 挂起议题（非代理）：签到「跳过」用了本地日期，可能与服务端日界不一致

状态：**待办，未实现**。赵总 2026-09-17 拍板"先记着，本轮不动"——
理由是它只会让奖励晚到、不会丢也不会重复领，而当时测试包已定稿，
再动代码就得重新打包并重出校验和。留到 v1.0.2 一起处理。

### 7.1 现象与位置

`src/daemon.js:625-628`（`checkinOneAccount`）：

```js
const date = checkinDateKey();          // Asia/Shanghai 本地日期
if (!force && account.checkin?.date === date && account.checkin.checkedInToday) {
  return { id: account.id, ok: true, skipped: true, reason: "already_checked" };
}
```

而成功路径（`daemon.js:673-682`）**无条件**把记录写成"今天已签"：

```js
await accountStore.saveCheckin(account.id, { date, checkedInToday: true, ... });
```

注意：即使 `result.claimed === false`（服务端本来就已签、这一轮没领到任何东西），
本地也会被标记成 `date = 今天` + `checkedInToday = true`。

### 7.2 为什么会不一致

签到的"今天"由**服务端**定义，接口只回 `checked_in: true/false`
（`trae-checkin.js:57` `parseCheckinStatus`），**不返回任何日期或重置时间**。
本地却用北京日期做键。两者日界不重合时：

1. 跨过北京 0 点 → 本地键翻页 → 不再跳过 → 去问服务端；
2. 服务端此刻仍在**上一个窗口**里，答"已签"；
3. 本地于是写下 `date = 新的一天` + `checkedInToday = true`；
4. 服务端真正翻页后，本地整天都在跳过 → 这一天的奖励要等到**下一次北京 0 点**才领到。

### 7.3 严重程度（两种日界都推演过）

- 服务端日界晚于北京 0 点：奖励**延迟**到次日 0 点领到，不丢。
- 服务端日界早于北京 0 点：日界到当天 24:00 之间被跳过，同样是延迟，不丢。
- 两种情况都**不会重复领**（领奖前先查 `fetchCheckinStatus`，是幂等的）。

真正的伤害是**面板显示会虚**：当前窗口其实还没签，界面却写着"已签到"。

**前提**：以上推断假设服务端日界是某个固定时刻。**这一条没有实测数据支撑**，
不能当成结论用。要确认只有两条路——在目标机器上观测一整天，
或抓签到接口看是否返回日界字段。

### 7.4 候选修法（择一时再说）

| 方案 | 做法 | 代价 |
|---|---|---|
| 观测优先 | 每小时把服务端 `checked_in` 的变化记一行到日志，跑一两天看出真实日界 | 只读，几乎无风险；需重打包 |
| 去掉本地跳过 | 每轮都向服务端确认真实状态 | 显示永远准；每账号每天请求数约 1 → 48，可能触及风控 |
| 精确跳过 | 记录"服务端答已签"的时刻，仅当它与本地键同属一个北京日时才允许跳过 | 逻辑变复杂，仍需知道服务端日界才算得准 |

**没搞清楚服务端日界之前不要动这块**：三种改法都建立在同一个未知量上。

## 8. 挂起议题：Cockpit 探测改为「只信确证在跑」

状态：**已拍板要做，但排到 v1.0.1 验收之后**（赵总 2026-09-17：
"尽量不要考虑 cockpit，这是非常罕见的情况" + "先不改，验收完再说"）。
理由：测试包 `dist/release/v1.0.1-test/` 已定稿出校验和，改代码就要重打包重出哈希，
而这一条不影响"能不能验收"，只影响"保活会不会白让路"。

### 8.1 现状为什么不对

`resolveCockpitPolicy()`（`src/daemon.js:609-619`）有三个分支：

| 探测结果 | 现在的动作 | 实际后果 |
|---|---|---|
| `running === true`（确证在跑） | `skip` | 让路，正确 |
| `running === false`（确证没跑） | `run` | 正常 |
| `running === null`（两个探针全失败） | `no-token-refresh` | **签到降级 + 保活整轮跳过** |

问题出在第三行。探针是 `tasklist.exe`（原生程序，比 PowerShell 难拦）优先、
PowerShell 兜底（`trae-process.js:188-191`）。若一台机器把两者都拦了
——企业加固的常见做法——探测**永远**返回 null，于是：

- **保活一次都不会跑**，永久失效；
- 签到虽然照跑，但 `allowTokenRefresh` 为 false（`daemon.js:1640`），
  快照里 token 过期时 `runFlow()` 抛 `authExpired` 会被直接 rethrow，
  **无法自愈**——这正是赵总那个 401 在受限机器上的表现形态。

也就是说，为一个罕见场景（真的有人同时开着 Cockpit Tools）付的代价，
是普通场景下主功能被关掉。这个取舍不成立。

### 8.2 怎么改

判断该不该让路，只认**确证在跑**这一种：

```js
async function resolveCockpitPolicy() {
  const probe = await probeCockpitTools();
  if (probe.running === true) return { action: "skip", probe };
  if (probe.running === null) {
    // 探不出来就当作没在跑：探测失败本身不该成为关掉主功能的理由。
    // Cockpit 同时运行是罕见场景，而探针被拦是受限机器上的常态。
    console.warn(`[cockpit] probe failed (${probe.error}); proceeding as if Cockpit Tools is not running`);
  }
  return { action: "run", probe };
}
```

`no-token-refresh` 这个中间态**整体删除**（`daemon.js:601-602` 的注释块一并更新）。
好处是唯一收敛点改一处，4 个调用方（`daemon.js:1049` / `1223` / `1632` / `1672`）自动跟随。

`probeCockpitTools()` 的**三态返回值保留**（`trae-process.js:193-204` 不动）：
`null` 仍然要能和 `false` 区分开，用于日志与诊断，只是不再产生"降级运行"的策略。

### 8.3 连带要改的地方

- `daemon.js:601-604` 的注释块（三态说明）与 `:1068`、`:1229-1230` 两处
  面向用户的提示文案——它们当前把"探不出来"描述成"保活被跳过"。
- `daemon.js:867` 有一句注释把"活跃身份读不到就整轮跳过"类比成"Cockpit 探针的同一规则"，
  改完这个类比就不成立了，必须一并修正，否则注释会误导后来的人。
- `src/ui/inject.js:2548` 提到"Cockpit 忙或被拦"时回退到 v1.0.0 的额度刷新路径，需复核是否还成立。

### 8.4 测试

现有测试**没有任何一条**锁住"探不出来"的行为（`test/trae-process.test.js`
只测了 `isCockpitImageName` 与 `parseTasklistImageNames`），所以改动不会被测试卡住，
但必须补上：

- 两个探针都抛错时 → 策略必须是 `run`，且日志里有 `probe failed`；
- 确证在跑时 → 仍然是 `skip`；
- 确证没跑时 → `run`。

### 8.5 需要赵总确认的残留风险

改完之后，唯一失去的防护是：**如果 Cockpit Tools 真在同时运行，且探针又被拦**，
两边会各自轮换同一批 refresh token，可能互相把登录顶掉。
按"罕见场景"的判断接受这个风险；若日后真撞上，回退方案是把探测改成
"只信确证在跑 + 额外比对 Cockpit 自己的配置文件时间戳"，而不是恢复现在的降级策略。
