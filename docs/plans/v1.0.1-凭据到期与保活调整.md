# v1.0.1 凭据到期显示与保活调整

> 状态：待赵总确认（未开工）
> 触发：赵总问「导出账号后本机刷新了 token，别的设备导入会不会 401」

## 一、实测结论（先看这个）

拿项目里同时存在的两份不同时间点的数据目录，比对同一账号的 refreshToken 哈希
（只输出哈希，不打印明文）：

| 账号 | 类型 | refreshToken 一致 | 备注 |
|---|---|---|---|
| `acct_0e6f…` | 非活跃 | **否** | `refreshExpiredAt` 2027-03-15 → 03-12 |
| `acct_e083…` | 非活跃 | **否** | `refreshExpiredAt` 2027-03-15 → 03-13 |
| `acct_5e1b…` | 活跃 | 是 | keepalive 记录 `syncedFromLive:true` |

**结论：TRAE 的 `ExchangeToken` 每次调用都换发新的 refresh token。**
一个账号在服务端只有一条有效凭据链 —— 谁刷新，谁就把别人踢掉。

活跃账号之所以相同，是因为它走「从 TRAE 实时存储同步」、不经过交换 —— 反向印证了结论。

**推论**：导出到别的设备 = **搬迁**，不是共享。两台设备同时管一个账号必然互踢（401）。
这是服务端机制，任何实现都绕不过，只能靠**降低轮换频率**来降低撞车概率。

`WorkDaddy` 管的是 **WorkBuddy 账号**（`www.workbuddy.cn`，
`POST /v2/plugin/auth/token/refresh`），与本项目的 TRAE 是**两套服务端** ——
策略可借鉴，机制不可照搬。

## 三、改动清单

### 1. 保活改为到期驱动 ★核心

**`src/lib/trae-keepalive.js`** 新增（保持纯函数，不引入 `trae-crypto` 依赖）：

```js
export const DEFAULT_ACCESS_TOKEN_THRESHOLD_MS = 24 * 60 * 60 * 1000;        // 1 天
export const DEFAULT_REFRESH_TOKEN_THRESHOLD_MS = 30 * 24 * 60 * 60 * 1000;  // 30 天

// 数字（秒 / 毫秒）或 ISO 字符串 → 毫秒；无法解析返回 null
export function toMillis(value) { ... }

export function shouldRotateCredentials(auth, {
  now, accessThresholdMs, refreshThresholdMs,
} = {}) {
  const accessExpiresAt = toMillis(auth?.expiredAt ?? auth?.expiresAt);
  const refreshExpiresAt = toMillis(auth?.refreshExpiredAt);
  if (accessExpiresAt === null) return true;                    // 缺字段 → 保守换票
  // refreshExpiredAt 等于 access 到期时间时，是写入端 fallback 出来的假值，忽略
  if (refreshExpiresAt !== null && refreshExpiresAt !== accessExpiresAt
      && refreshExpiresAt - now < refreshThresholdMs) return true;
  return accessExpiresAt - now < accessThresholdMs;
}
```

- 缺字段 → 换票，与 WorkDaddy 的 `expiresAt === null → true` 一致。
- 最后一行的 fallback 防护：`trae-refresh.js:116` 在服务端不给 `RefreshExpireAt` 时，
  会拿 access 的到期时间兜底，直接判断会**恒真**（每次换票），必须排除。

**`src/lib/trae-refresh.js`**：

- 抽 `readAuthFromSnapshot(snapshot)`（`refreshAuthSnapshot` 内已有那段解析，复用）
- `refreshAccountKeepalive(snapshot, { now })` 改为：
  1. `shouldRotateCredentials(auth)` 为真 → `refreshAuthSnapshot` 换票
  2. `fetchTraeAccountInsights` 同步额度
  3. 抛 `TraeInsightsAuthError` 且本步还没换过票 → 换票后**重试一次**
  4. 返回值 `refreshedToken` 反映真实情况（原实现写死 `true`）

**`src/daemon.js`**：

- `keepaliveOneAccount:777` 的 `tokenRefreshed: true` → `refreshed.refreshedToken`
- `saveKeepalive` 载荷加 `accessExpiresAt` / `refreshExpiresAt`
  （取 `refreshed.auth.expiredAt` / `refreshExpiredAt`）
- `keepaliveActiveAccount:824` 同样写这两个字段（从快照读，`tokenRefreshed` 仍是 `false`）

**不动**：`isKeepaliveDue`、6 小时节奏、30 分钟扫描间隔 —— 扫描只负责触发额度同步。

**预期效果**：

| | 现在 | 改后 |
|---|---|---|
| 换票频率 | 每天最多 4 次 | ≈ 每 11~14 天 1 次（access token 寿命决定）|
| 额度同步 | 6 小时 | 6 小时（不变）|
| 与其他设备 / Cockpit Tools 撞车 | 高 | 低 |

### 2. 面板把「保活」换成凭据到期时间

**现在**：`inject.js:1399` `accountKeepaliveView()` 只给「正常 / 失败 / 待保活 / 运行中」，
`inject.js:1564` 标签写死「保活」—— 赵总说看不懂。

**改成**：标签「保活」→「凭据」，值显示到期时间，四档着色（照 WorkDaddy `inject.js:10514`）：

| 档位 | 显示 | 颜色 class |
|---|---|---|
| 已过期 | `已过期` | `error`（红，已有）|
| 剩余 < 24h | `即将过期` | `error`（红，已有）|
| 剩余 < 7 天 | `X 天后` | `warning`（橙，**新增一条 CSS**）|
| 其它 | `MM-DD 到期` | `checked`（绿，已有）|

- 活跃账号仍显示「运行中」（由 TRAE 会话维护，不参与轮换）
- tooltip 补齐：`登录凭据 10-01 到期 · 长期凭据 2027-03-15 到期 · 最近同步 09-18 00:30`
- 数据来自改动 1 写进 `keepalive` 的两个字段 —— **不改 index schema，不改 `publicAccount`**

### 3. 导出 / 导入写明「搬迁」语义

`openTransferDialog()` 返回 body，在导出与导入两个弹窗的 body 顶部插一段说明：

> 导出的是一份**凭据快照**。导入到其他设备后，**本机上的该账号会被顶下线**，
> 需要重新登录才能恢复 —— 这是搬迁，不是共享。不要在两台设备上同时管理同一个账号。

新增一条最小 CSS（`.te-transfer-note`），复用现有字号与色值。

### 4. About 文案

`inject.js:1066`：「为非当前账号定期刷新登录凭据和额度。」
→ 改为说明「仅在临近到期时刷新」，避免与新的到期驱动策略矛盾。

## 四、不做什么

- **不改 `ExchangeToken` 的调用方式** —— 它必然轮换，改不了
- **不做多设备协调** —— 没有中心服务，做不到
- **不动 `isKeepaliveDue` 与扫描节奏** —— 额度同步频率保持 6 小时
- **不动签到 / 额度已有的按需刷新** —— 本来就是对的
